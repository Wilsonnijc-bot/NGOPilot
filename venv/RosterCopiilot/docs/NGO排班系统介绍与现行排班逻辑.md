# NGO 排班系统介绍与现行排班逻辑

> 面向读者：Oscar、产品团队、刚接触项目的开发者<br>
> 更新日期：2026-07-14<br>
> 当前稳定基线：v0.5.0；Phase 1B（来源追溯、审核与正式发布闭环）正在实施

## 1. 先用一句话理解这个系统

RosterCopiilot 的目标是把 NGO 目前依靠 Excel 和人工经验完成的每周排班，变成：

```text
系统根据固定服务、当周需求、员工资料和 NGO 规则起草排班
                    ↓
主管检查不确定、未分配和临时改动
                    ↓
系统输出员工熟悉的「照顾员工作分工表」Excel
```

系统替代的是“人工制作初稿”这一步，不替代主管审核，也不会自动把未经确认的排班发给员工。

这不是一个单纯的 Excel 合并工具。Excel 是业务资料和输出载体，真正完成排班的是中间的规则、任务生成、资格检查、候选排序、局部重排和独立验证。

## 2. NGO 目前的问题是什么

现有排班同时包含多种性质不同的工作：

- 长者每周或每月固定发生的家居服务；
- 运动训练、家居清洁、个人护理和冲凉等个案服务；
- 每周都会变化的护送、陪诊需求；
- AMC、MRC、GC 等中心的当值需要；
- 送饭、厨房和其他支援工作；
- 员工请假、长者取消、住院、新增或取消护送等临时变化。

困难不只是“把名字填进空格”，而是同时保证：

1. 员工具备相应技能，并且当时有空；
2. 身体接触服务满足性别要求；
3. 专属个案不被随意换人；
4. 护送、固定服务和中心当值不会撞期；
5. 中心不能缺少必要当值人员；
6. 临时变化尽量只影响少量已有安排；
7. 无法确定的资料必须显示出来，不能由系统暗中猜测。

因此，这个问题本质上是“有硬规则、有偏好、有临时变化、需要人工负责最终决定的排班问题”。

## 3. 逆向工程使用了哪些资料

规则主要来自会议转录、需求摘要和 NGO 提供的 Excel。三张核心工作簿各自承担不同角色。

| 文件 | 我们从中理解到什么 | 当前 Demo 中的角色 |
| --- | --- | --- |
| `照顧員工作分工表2026(HKU).xlsx` | 员工列、星期/上下午格位、固定安排、ESC 预留位、中心当值、送饭、颜色和备注语义 | 系统内置的固定基础和输出模板，不需要每次上传 |
| `2026_HC 時間表(HKU).xlsx` | HC、PC、B 等服务的日期、星期、时段、节数和改期信息 | 用户上传；筛选目标周内的服务需求 |
| `護送個案總表(2026)(HKU).xlsx` | 护送日期、上下午、应诊时间、目的地、科目、交通、备注和员工偏好 | 用户上传；筛选目标周内的护送需求 |
| `新同工跟服務紀錄表` | 新员工做过哪些服务、中心工作和送饭路线 | 技能和路线资格的证据，但资料只覆盖部分员工 |
| `個案轉移紀錄` | 个案换员工、换日期、换时间及生效日期 | 有效期变化的证据；TBC 不能直接当成已确认事实 |

完整的逆向工程结果位于：

- [excel_semantics.md](spec/excel_semantics.md)：解释每张 Excel 的布局和颜色、合并格、备注等业务语义；
- [data_dictionary.md](spec/data_dictionary.md)：解释字段、服务代码、单位、地区和节数；
- [rulebook.md](spec/rulebook.md)：整理正式业务规则、优先级、证据和待确认问题；
- [rescheduling_algorithm.md](spec/rescheduling_algorithm.md)：描述请假、取消和新增护送后的重排逻辑；
- [human_review_policy.md](spec/human_review_policy.md)：规定哪些情况必须由人审核。

逆向工程采用四种可信度标记：

| 标记 | 意思 |
| --- | --- |
| `E` / `[C]` | 会议或表格明确支持，可以较有把握使用 |
| `S` / `[I]` | 证据强烈暗示，但仍属于推断 |
| `W` | 弱推断，只能作为讨论线索 |
| `U` | 不清楚，必须向 NGO 确认 |

核心原则是：**推断可以帮助系统提出建议，但未经确认的语义不能偷偷升级成硬规则。**

## 4. 三张核心 Excel 的关系

### 4.1 照顾员工作分工表：总盘和输出格式

这张表是员工最终阅读的总排班，也是我们理解固定安排的主要基础。它包含约 46 个可识别员工列，按星期、上午/下午和格位排列工作。

它告诉系统：

- 哪位员工通常跟哪个固定个案；
- 每个服务在星期几、上午还是下午；
- 哪些格位预留给 ESC；
- 谁通常负责中心当值、送饭或其他工作；
- 员工工作时间、星期六 A/B 更和部分备注限制；
- 导出的 Excel 应保留怎样的合并格、颜色、列顺序和视觉结构。

它不是每周都要重新上传的“需求表”，而是固定基础和输出模板。

### 4.2 HC 时间表：按月展开的家居服务需求

这张表补充主分工表中不容易表达的月度规律，例如：

- 某长者只在每月第 1、3 周接受服务；
- 某服务在第 2、4 周发生；
- 单月或双月才发生；
- 本次服务改到其他日期或时间；
- `只要某员工` 等专属或偏好备注。

当前系统把“第 N 周”解释为该星期在当月的第 N 次出现。例如“星期三第 2 周”是当月第二个星期三。这是工作假设，仍需 NGO 最终确认。

### 4.3 护送总表：每周浮动的具体需求

每一行代表一项具体护送需求，常见字段包括：

- 日期及上午/下午；
- 长者代号；
- 应诊时间和目的地；
- 科目、交通工具和备注；
- 提早接送要求；
- `只要某员工` 或 `尽量安排某员工` 等绑定与偏好。

当前系统把一项护送视为占用整个上午或下午。这是为了在缺少可靠结束时间和交通时间时避免撞期，也是需要 NGO 确认的保守假设。

## 5. 系统真正需要的输入

### 5.1 长期维护的基础资料

正式系统不能只依靠 Excel 中零散出现的名字。它需要 NGO 维护以下 master data：

| 资料 | 关键字段 |
| --- | --- |
| 员工 | 短名/别名、队伍、性别、技能、可做路线、中心资格、工作时间、星期六组别 |
| 长者 | 代号、所属单位、地区、状态、性别或性别要求、专属员工 |
| 固定服务 | 服务类型、星期、时段、节数规律、员工绑定、是否专属、生效日期 |
| 规则配置 | 中心当值人数、时段定义、护送容量、星期六轮换、优先级和未知资料政策 |
| 人工覆盖 | 某个格位不可加 Case、临时指定员工、主管确认的例外 |

当前 Demo 已经可以持久化版本化的基础资料，但部分技能、性别、路线和当值人数仍使用 seed 或工作假设。正式试运行必须由 NGO 补全和确认。

### 5.2 每周输入

当前 Demo 的每周输入是：

1. 上传 HC 时间表；
2. 上传护送总表；
3. 选择目标周，系统自动对齐到星期一；
4. 输入临时变化：员工请假、长者取消、取消护送或新增护送。

系统只采用星期一至星期六、且真正落在目标周内的记录。目标月份不匹配时只显示警告，不会虚构需求。

长期产品不应要求 NGO 每周上传三张工作簿。更合理的方向是：基础资料在系统内维护，每周只输入新增需求和变化；目前上传两张表是为了让 Demo 连接 NGO 现有工作方式。

## 6. 系统内部如何表示排班

理解以下四个概念，就能理解大部分代码：

| 概念 | 通俗解释 | 示例 |
| --- | --- | --- |
| `MasterData` | 长期事实 | 员工娥会做 HC；长者 L容需要 PC |
| `TaskDemand` | 本周必须处理的一项具体需求 | 2026-05-07 上午为 L容提供 PC |
| `ScheduleEntry` | 系统建议的实际安排 | 建议员工娥在该时段执行这项 PC |
| `AuditItem` | 主管必须知道或决定的问题 | 员工性别资料缺失；该安排需要确认 |

排班系统不是直接从 Excel 单元格跳到另一个 Excel 单元格，而是先把输入转换为统一的本周任务，再为任务寻找员工。

## 7. 从输入到输出的完整流程

```text
内置分工表 + 系统基础资料
          +
上传 HC 表 + 上传护送表 + 临时变化
          ↓
1. 解析并保留来源、备注和疑点
          ↓
2. 建立本周 SchedulerSnapshot
          ↓
3. 将周期服务展开为有具体日期的 TaskDemand
          ↓
4. 建立基线排班：固定服务 → 护送 → 中心当值
          ↓
5. 应用请假、取消和新增护送，进行局部修复
          ↓
6. 独立验证所有已接受安排
          ↓
7. 汇总未分配、审核项目、影响和来源证据
          ↓
8. 匯出前检查每项安排能否安全写回 Excel 格位
          ↓
9. 生成「照顾员工作分工表_审核草稿.xlsx」
```

排班引擎本身不读取 Excel。Excel 由上游解析成统一资料后，排班引擎只处理员工、长者、任务、规则和变化事件。这使规则可以测试，也避免排班逻辑依赖某个单元格位置。

## 8. 当前基线排班的具体逻辑

当前引擎是确定性的 greedy scheduler：不使用 LLM，也不使用 CP-SAT。相同输入会得到相同选择，方便解释和测试。

### 8.1 第一步：生成本周任务

系统把不同来源转换为具体日期的任务：

- 每周固定服务直接落到相应星期和时段；
- `1,3`、`2,4`、单双月等服务先判断目标日期是否匹配；
- HC 上传只选择目标周内的记录；
- 护送上传只选择目标周内的预约；
- 每个中心每个时段的需求人数展开成对应数量的当值任务；
- 目标周外或节数不匹配的资料记录为“本周不发生”，不算未分配任务；
- 无法解析或资料不足的记录进入资料缺口或审核，不静默丢弃。

### 8.2 第二步：安排固定服务

固定服务代表已经对长者形成的承诺，因此基线排班先尝试保留原员工：

1. 如果原员工符合全部硬规则，保留原安排；
2. 如果原员工不可用，但服务不是专属服务，寻找合资格替代员工；
3. 替代安排标记为 `needs_review`，并给主管候选理由和其他备选；
4. 如果服务是专属服务，原员工不可用时默认建议取消，不自动换人；
5. 如果没有任何合资格员工，任务成为 `unassigned`，并产生阻塞审核。

### 8.3 第三步：安排护送

护送是时间固定、占用半日且对性别和偏好敏感的需求：

1. 先筛除没有护送资格、请假、撞期或不符合绑定的员工；
2. `只要某员工` 被视为强绑定；`尽量安排某员工` 只提高该员工排名；
3. 在可用候选中按统一排序选择第一名；
4. 没有可用候选时，任务进入未分配和阻塞审核；
5. 内置分工表中的 ESC 格位用于理解预留容量，但实际安排以目标周的具体护送请求为准。

### 8.4 第四步：补中心当值

固定服务和护送安排后，系统用剩余可用人手补 AMC、MRC、GC 的当值人数：

1. 每个中心、日期和上下午都有一个需要人数；
2. 优先选择熟悉该中心、当前工作量较少、当值次数较少的合资格员工；
3. 如果仍达不到最低人数，产生 `duty_under_coverage` 阻塞审核；
4. 中心当值缺口不会被静默忽略。

### 8.5 为什么“中心当值优先级最高”，却最后才补

这里有两个不同概念：

- **构建顺序**：固定服务先放，护送其次，中心当值最后使用剩余人手补齐；
- **业务保护优先级**：中心当值缺口最严重，其次是护送、家居服务、送饭和其他工作。

中心当值像一个必须达到人数下限的“容量池”。最后补可以避免它过早占掉已有固定承诺；但如果补不齐，它会成为最高级别问题。临时取消释放人手时，系统也会优先拿这段空档补中心当值。

当前代码中的优先级层级是：

| 层级 | 工作 |
| --- | --- |
| 1 | AMC、MRC、GC 中心当值 |
| 2 | 护送/陪诊 |
| 3 | 运动训练、HC、PC、冲凉 |
| 4 | 送饭 |
| 5 | 厨房及其他后勤工作 |

这个层级主要用于缺口严重度、重排保护和是否允许低优先级工作被调动，不等同于简单的代码执行先后。

## 9. 员工是否可以接任务：硬规则

候选员工必须先通过共同的资格检查。当前已实现的主要硬规则包括：

| 规则 | 当前行为 |
| --- | --- |
| 技能 | HC、PC、B、ESC、运动训练和中心工作需要相应技能 |
| 性别 | PC、B 和部分护送需要满足长者/个案性别要求 |
| 专属绑定 | 专属服务只能由指定员工完成；缺席时建议取消 |
| 护送 must 偏好 | `只要某员工` 限定为该员工，不当作普通偏好 |
| 请假和工作日 | 请假时段不可安排；星期六按 A/B 更；星期日不排 |
| 人工容量锁 | `不可加Case` 等覆盖会禁止在该员工格位新增工作 |
| 时间容量 | 同一员工不能在同一时段重复安排；护送占整个半日 |
| 未知关键资料 | 根据资料缺口政策变成不可分配或待审核，不可成为普通已确认安排 |

当前排班以“上午/下午 + 节次”为主要时间粒度，还没有完整实现分钟级交通时间和所有员工的精确工作时段约束。

## 10. 多个合资格员工之间怎么选

硬规则只回答“能不能做”。如果多人都能做，当前系统依次比较：

1. 地区或路线是否匹配，减少跨区；
2. 是否需要依赖 seed 或尚未确认的技能/路线，优先选择证据较可靠的候选；
3. 是否是个案记录中的建议员工；
4. 本周已经安排的工作量，优先较轻者；
5. 是否熟悉该中心；
6. 中心当值次数是否较少，促进轮换公平；
7. 员工稳定 ID，作为最后的固定排序，保证结果可重复。

需要注意：当前实现只是“地区/路线是否匹配”，还不是基于公共交通分钟数的完整 travel matrix。逆向工程文档中的“减少交通时间和来回折返”是目标逻辑，尚未全部实现。

## 11. 临时变化如何重排

系统不会因为一个变化把全周完全洗牌，而是在原基线之上做局部 repair，尽量保持未受影响的安排不动。

### 11.1 员工请假

- 找出该员工当天或半天的全部安排；
- 专属服务建议取消并阻塞审核；
- 非专属服务寻找替代员工；
- 替代建议标记为待审核，并保留其他候选；
- 找不到替代时进入未分配；
- 所有建议都记录“为什么受影响、为什么选择这个人”。

### 11.2 长者取消服务

- 对应服务标记为取消；
- 原员工释放出来；
- 如果同一时段中心当值不足，优先建议该员工补当值；
- 如果没有缺口，明确记录该员工暂时空出，而不是制造没有需要的工作。

### 11.3 取消护送

- 释放原护送员工的半日容量；
- 优先检查能否补中心当值缺口；
- 记录影响和审核信息。

### 11.4 新增护送

- 先找当时段完全空闲且合资格的员工；
- 如果没有，当前代码可以尝试一次深度的连锁调动：让某员工接护送，再为其原本较低优先级工作寻找替代；
- 整条调动链作为一个高风险审核项目展示；
- 没有可行方案时，护送保持未分配并阻塞发布。

多个事件按“先释放容量、后消耗容量”的顺序处理：取消服务、取消护送、员工请假、新增护送。这样可让前面释放的人手用于后面的需求，并保证处理结果稳定。

## 12. 排班完成后为什么还要再检查

排班器和验证器是两套独立步骤。排班器提出安排后，验证器从头检查：

- 员工是否存在和有技能；
- 性别要求是否满足；
- 专属和 must 绑定是否违反；
- 是否请假、OFF、星期日工作或被人工禁止；
- 是否同一节或同一半日撞期；
- 普通 `scheduled` 项目是否偷偷使用了 seed、低可信度或未解决资料。

只看“排班器说成功”是不够的。独立验证必须得到零个硬规则违反，才能继续进入 Excel 匯出前检查。

## 13. 来源追溯和任务守恒

Phase 1B 正在强化以下链条：

```text
Excel 行/基础资料/临时变化/规则假设
              ↓
         本周任务 demand_id
              ↓
       排班条目 ScheduleEntry
              ↓
       审核项目和人工决定
              ↓
       Excel 中的准确工作表和格位
```

每一项本周需求最终必须且只能处于一种状态：

- 已安排；
- 待审核安排；
- 未分配；
- 已确认取消；
- 有审核记录的明确抑制。

目标是避免出现“输入中有一项服务，但后来不知道去了哪里”的情况。来源、资料缺口、审核 ID 和 Excel 格位最终应能互相追溯。

## 14. 人工审核与发放状态

系统输出三种发放状态：

| 状态 | 含义 |
| --- | --- |
| `可发放 / ready` | 没有硬规则违反、未分配和待处理阻塞审核 |
| `草稿需审核 / draft` | 没有硬规则违反，但仍有非阻塞项目需要确认 |
| `不可发放 / blocked` | 存在硬规则问题、未分配、中心缺人或其他阻塞审核 |

典型阻塞项目包括：

- 专属服务取消；
- 未分配任务；
- 中心当值人数不足；
- 连锁调动；
- 规则冲突或 Excel 无法安全落格。

目前 `review_export_allowed=true` 只表示系统可以安全生成一份标明状态的审核草稿，不表示可以交给员工。只有 `publication_state=ready` 才代表具备正式发放条件。

## 15. 输出 Excel 包含什么

下载文件为：

```text
照顧員工作分工表_審核草稿.xlsx
```

主要工作表包括：

| 工作表 | 内容 |
| --- | --- |
| `恆常服務` | 按原 NGO 布局写入排班草稿 |
| `RC_變更摘要` | 输入文件、目标周、临时变化和生成摘要 |
| `RC_審核` | 审核项目、原因、规则、来源和关联安排 |
| `RC_未分配` | 无法安排或无法安全写入主表的任务 |
| `RC_meta` | 版本、发放状态、验证和写入统计 |

系统保留原来的员工列、合并格、行高、列宽和业务颜色。新增或改变的格位使用附加边框和批注，不覆盖原颜色语义。需要审核的批注以 `RC:待審` 开始并带审核 ID。

## 16. 已实现、工作假设与尚未完成

### 已经实现

- 内置分工表 + 上传 HC/护送 + 临时变化的真实输入链路；
- 周期任务展开和确定性基线排班；
- 请假、取消、新增护送的局部重排；
- 技能、性别、专属、请假、撞期和周末规则检查；
- 中心当值缺口、未分配和人工审核；
- 独立验证器和匯出前安全检查；
- 保留 NGO 格式的 Excel 审核草稿；
- 版本化 master data；
- 来源追溯和任务守恒的 Phase 1B 基础正在实施。

### 当前工作假设

- 护送占用整个上午或下午；
- “第 N 周”按该星期在当月第 N 次出现计算；
- 内置表推算的中心当值人数和 ESC 预留容量可用于 Demo；
- 部分员工 seed 技能可让 Demo 运作，但必须显示资料缺口；
- 地区匹配暂时代替完整交通时间计算。

### 仍需 NGO 确认或提供

- 全部员工的性别、技能和可做路线；
- 长者性别要求和专属员工；
- 每个中心、每个时段、不同角色的最低人数；
- 星期六 A/B 更的准确轮换锚点；
- “第 N 周”“长周”“BL”等真实定义；
- 护送是否默认同性、能否一人半日连续护送两个个案；
- 精确工作时间、午饭保护、服务时长和交通时间；
- `安排某员工` 与 `建议/尽量安排某员工` 的 must/prefer 文字规则；
- 正式主管的审核、例外和发布权限。

## 17. 当前系统不是什么

- 不是让 LLM 根据文字自由决定排班；
- 不是已经完成的全局最优路线规划器；
- 不是把三张 Excel 每周机械合并；
- 不是未经主管批准就自动发放的系统；
- 不是遇到缺失资料就自动猜答案的系统；
- 不是当前就能完全替代 NGO 原排班负责人的生产系统。

当前最准确的定位是：**真实输入驱动、规则明确、结果可解释、能够安全输出 NGO 格式的自动排班审核草稿系统。**
