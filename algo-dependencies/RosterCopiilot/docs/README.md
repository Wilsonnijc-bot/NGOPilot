# RosterCopiilot 文档导航

本目录同时保存产品说明、规则逆向工程、持续记录、原始证据和未来
设计。不同目录的权威性不同；不要把历史审查或未来方案当成当前能力。

## 从这里开始

- [NGO 排班系统介绍与现行排班逻辑](NGO排班系统介绍与现行排班逻辑.md)：
  面向 Oscar 和新成员的系统性中文介绍。
- [Demo 使用说明](使用說明.md)：面向 NGO 工作人员的启动和操作步骤。
- [当前规格索引](spec/README.md)：产品、工程、规则和 Phase 1A/1B 的
  当前权威文档。

## 目录边界

| 目录 | 内容 | 是否代表当前实现 |
| --- | --- | --- |
| `spec/` | 当前产品边界、业务规则、领域模型、排班和发布契约 | 是；但每份文档仍应看状态说明 |
| `ngo/` | 持续更新的 NGO 澄清问题和资料收集模板 | 是，属于待确认输入，不是已确认规则 |
| `records/` | 事实核验、测试覆盖等持续记录 | 记录事实与状态，不单独定义产品行为 |
| `evaluation/` | 当前 mock 数据和指标说明 | 部分已实现；以代码和测试为最终依据 |
| `reference/` | 导入器等辅助工具说明 | 仅开发参考，不是用户主流程 |
| `future/` | CP-SAT、目标 benchmark 等未实现设计 | 否，禁止据此宣称现有能力 |
| `legacy/` | 已完成或被取代的历史审查 | 否，只供追溯 |

## 维护规则

1. 当前行为变更时，先更新 `spec/` 中相应契约，再更新代码和测试。
2. 新的 NGO 回答追加到 `ngo/`，并把已确认结论同步回 `rulebook.md`。
3. 事实核验和覆盖状态写入 `records/`，保留日期和证据，不删除历史结论。
4. 未实现方案只能进入 `future/`，必须明确写出非当前能力。
5. 已被新规格完全取代、但仍有审计价值的文件移入 `legacy/`。
6. 只有既无证据价值、又无引用、也不可能支持回归或审计的文件才删除。
